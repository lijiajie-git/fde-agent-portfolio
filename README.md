## 作品一：川财 Agent 编排

**怎么看**：打开后右上角下拉框里有 7 条真实运行记录。按空格键播放或暂停，按 ← / → 一步一步看。点画布上的节点或底部的步骤，底部面板会显示这一步的输出、Prompt 原文、工具参数与返回、校验结果和数据来源。

### 1. 业务背景

券商投行部做 ABS（资产证券化）业务时，发票核对、合同字段抽取、底稿归档、Excel 填表这些活重复多、量大，而且一个数字都不能错。我在川财证券实习期间，从零搭了一套只在本机运行的 Agent 工作流来接这些活。这个 HTML 回放的就是它真实跑过的记录。

### 2. 解决什么问题、怎么解决

用户给一句任务和一批文件，Agent 分四步处理：

- **意图门**：先判断这句话在不在业务范围内。无关问题直接拒绝，说得不清楚就追问，发现 prompt 注入就拦下，三种情况都不往下走。它只看用户原话和附件的数量、扩展名，不看文件内容；模型调用失败时一律不放行。
- **Router 选包**：Router 只读用户的话和 5 个能力包的公开目录，选出该用哪个包（材料分类、发票核对、合同字段抽取、底稿归档、可信填表），看不到业务工具和标准答案。输出只允许"选哪些包 / 缺什么输入 / 复杂度"三个字段，多一个字段就拒绝。
- **执行器 + 工具**：执行器把安全规则、能力包指令、业务 policy、工具 schema 和文件清单拼成 prompt，模型只负责决定调用哪个工具、填什么参数。
- **确定性校验 + 人工闸卡**：去重、加总、大小写金额互校、金额 + 税额 = 价税合计，这些都由代码完成（用 Decimal 算），不让模型自己算钱。金额、日期、扫描件这类敏感结果只出候选值，交给人核。

例子（"发票勾稽"那条记录）：两个路径下其实是同一张发票的副本。Agent 按发票号去重，2 张变 1 张，暂计 ¥30,000,000.00，同时标出"待人工 · 必核 2 份"。

### 3. Agent 编排设计

- 主链是一条线：意图门 → Router → 单个执行器调工具（每步只调一个，参数不符合 schema 就拒绝执行）→ 确定性校验 → 门禁或人工。被意图门拦下的请求不会调用 Router，画面上也就没有 Router 节点。
- 7 条记录覆盖成功、批处理、失败、安全门几种情况：发票去重（成功）；5 张截图分两块归档（批处理，中间调了视觉模型）；归档提交参数类型错误被拒（失败）；意图门放行后进入材料分类，视觉模型报错，执行器如实弃答；以及意图门的拒绝、追问、拦截各一条。全部是真实运行记录，没有重跑模型。
- 回放页把运行记录转成统一的事件流（span 的开始和结束、人工闸卡），画面状态完全由"到当前时刻为止发生过的事件"算出来。所以随便拖动进度条，同一时刻看到的画面都一样。
- 画布上只放节点名和连线。Prompt 原文、参数、校验数字都收进底部面板。记录里没有的字段标"未记录"，不补；合成的耗时前面加 `~`，和实测耗时分开。

### 4. 优势

**评测集设计**

- 评测题和标准答案分开存放：Agent 答题的进程读不到答案，判分另起一个进程事后对答案。
- 题目、prompt、policy、schema、判分器的版本都用 hash 冻结，改了任何一样，旧结果就不能直接拿来比。
- 同一道题跑两次：一次直接给正确的能力包，一次让 Router 自己选。这样能分清错在"选错包"还是"包没执行好"。
- 安全违规、改动原件、绕过人工闸卡单独计分，不会被平均准确率掩盖。
- 发票核对出了 7 道真题，覆盖 6 类最容易出事的情况，另加 1 道"本该走别的包"的路由题。修复扫描件读取问题后，从 5/7 提到 7/7，Router 7/7 全部选对。
- 意图门单独评测：37 题对 36 题，8 条注入全部拦下，17 条正常任务误拒 1 条，都附 Wilson 95% 置信区间。
- 弱项照实报。比如底稿归档那轮共 47 道题、225 个文件判断，其中担保机构一类只对了 7/62，没有藏起来。历史项目数据只算回归集，不当成 held-out。

**克制的编排选择**

- 用单执行器，不用多 agent。底稿处理要写文件、前后步骤互相依赖、几乎没有能并行的部分，拆成多个 agent 只会多付协调成本和 token。
- 加意图门时没改已冻结的 Router 契约，而是在它前面单独加一道门；Router 也不加"理由"之类的额外字段。
- Router 只看用户的话和公开目录；算钱、核对、写文件都交给确定性代码。模型不能自己确认写入：写 Excel 前要人确认两次，确认用的 token 由后端生成并消费。
- 曾经做过 hash 链、签名锚点这样的重审计层，评估后认为复杂度超出实际需求，就删掉了，收敛成 SQLite 台账加文件锁。
- 回放页本身也一样克制：只用一个强调色，而且只用在"正在发生的那一步"上；解释性文字不放在画布上。

## 作品二：飞书看板脱敏作品

**怎么看**：顶部是 4 个页签（总览、食品安全、业绩、履约）和门店类型筛选。点总览里的任一门店，会跳到它所在的专业页并选中这家店。

### 1. 业务背景

这是一个我做过的项目脱敏出来的版本给一个茶饮咖啡加盟品牌的区域督导做"加盟商日常管理看板"。数据是面试方提供的外部版底稿：60 家加盟店（乡镇店 49 家、商业区店 11 家），覆盖 3/13–3/16 四天，观察日为 3/16；门店、地区在底稿里就已是代号（1001 店、B 市等）。

### 2. 解决什么问题、怎么解决

督导没办法每天把 60 家店逐一看一遍。只看单一指标的话，要么所有店都报警，要么误伤正常的店。所以看板只回答一个问题：**今天先看哪几家，为什么。**

- **总览**：只汇总三个专业页的结果，不重新算综合分。
- **食品安全**：观察日的过期物料事实按记录数排序，取前 7 家；"效期疑似"（33 店）和"流程 / 设备"（37 店）两类只进入核对和补证流程，不占督导的主排名。
- **业绩**：连续两天比同类型门店基准低 5 个百分点以上的店进入候选（共 10 家），按两天平均差排序，首屏显示前 4 家。
- **履约**：按即时单"每杯均时"从高到低，取前 5 家；异常时段只作为核查背景。

数据链路：清洗 → 计算信号 → 独立验证，验证通过后才允许生成这个 HTML。生成脚本只改字段名、换算单位，不重新计算任何信号或排名。缺数据提醒和食安通知真实发到过测试群；没有真实跑过的环节，页面上统一写"尚未运行"。

### 3. 看板设计

**口径设计**

- 食安、业绩、履约分成三条泳道，不合成一个综合分，因为食安红线不能被业绩好抵消。
- 业绩和同类型门店的基准比，单位是百分点。切换门店类型时只做筛选，不在页面里重新排名。
- "每杯均时"是近似口径，不是总部 SLA。底稿里只有异常时段的记录，没有正常时段作分母，所以不算超时率。
- 缺订单明细的门店（如 1015 店）不填 0，单独标"缺订单明细"。
- 只有 4 天数据，不做周 / 月趋势；杯数字段存在口径冲突，不放进业绩主图。

**AI 分析**

- 共 23 条 AI 建议，由大模型基于已验证的看板数据和清洗明细生成。每条只有"一句发现 + 一句建议"，例如"1015 店业绩跌幅第 1，但 4 天都没有订单明细 → 先电话确认营业和数据上报"。
- 生成看板时会校验：建议里提到的门店必须真实存在，发现和建议都不能为空。
- AI 只给建议，不改动排序。建议是静态草稿，数据重跑后要重新生成。

**对用户注意力的克制**

- 前 7 / 前 4 / 前 5 是督导首屏能处理的容量，不是业务阈值，页面顶部写明了这一点；其余门店要点"展开"才看到。
- 业绩排行榜不用颜色深浅表示风险；食品安全页签也不用红色。
- 疑似类记录不进主排名；没有真实运行记录的环节，不显示发送数和回复数。
- AI 卡片去掉了"自动化建议""待督导确认"等附加标签，只留一句发现、一句建议。

### 4. 优势

- **口径诚实**：事实、规则候选、业务结论分开写。看板只说"原表存在这条记录"，不替业务认定原因、责任，也不认定问题已经处置完毕。
- **AI 有边界**：AI 建议引用的门店必须在数据里，只补充"该先做什么"，不改变排名。
- **省督导的注意力**：每页首屏只放督导当天处理得完的数量，其余进入通知或待排期，不在主屏上堆数字。
